## 0. คำถามที่ต้องตัดสินก่อนเริ่ม

แต่ละข้อมีค่าที่แนะนำ ถ้าไม่ตอบ plan นี้ใช้ค่าที่แนะนำ

1. **เรียกซ้อนตอนที่มี dialog เปิดอยู่ ค่าเริ่มต้นเป็นซ้อน (stack) หรือต่อคิว (queue)?** แนะนำ `stack` เพราะตรงกับ #46/#47 ซึ่งเป็นกรณีที่คนเจอบ่อยกว่า (เปิด dialog จากใน dialog) ส่วน #72 ใช้ `strategy: 'queue'` ต่อครั้งได้ ถ้าเลือก queue เป็นค่าเริ่มต้น dialog ที่เปิดจากในอีก dialog จะค้างรอจนตัวแม่ปิด ซึ่งคือ deadlock ในกรณี nested
2. **หน้าตาเริ่มต้นจะคงแบบ v3 หรือออกแบบใหม่?** v3 ใช้ overlay สีขาว 90%, ปุ่มดำ, กว้าง 400px, ชิดซ้าย แนะนำคงโครงเดิม (ผู้ใช้ 250k/เดือนจะไม่ตกใจ) แต่เปลี่ยนค่าเป็น CSS custom property ทั้งหมด ลบ delay 0.2s ตอนเปิด และเปลี่ยน blur จาก SVG filter เป็น `::backdrop { backdrop-filter }` นี่เป็นเรื่องรสนิยมของเจ้าของ lib ทดลองตัดสินไม่ได้
3. **ยอมตัด browser ที่ไม่มี `<dialog>.showModal()` หรือไม่?** ต้องการ Chrome 37+, Firefox 98+, Safari 15.4+ (มีครบตั้งแต่มีนาคม 2022) แนะนำยอม และไม่ใส่ polyfill ถ้าต้องรองรับ Safari เก่ากว่า 15.4 ต้องกลับไปใช้ div overlay และ focus trap ที่เขียนเอง ซึ่งเพิ่มขนาดราว 1 kB gzip (ประเมิน ยังไม่ได้วัด)
4. **default export `ReactConfirmAlert` (class component) จะเก็บไว้ไหม?** v3 export ไว้แต่ใช้ตรง ๆ ไม่ได้จริง เพราะ `close()` ไป unmount root ที่ module สร้าง (`src/index.js:63-68`, `:199-204`) แนะนำเก็บเป็น alias ที่ deprecate แล้วให้ชี้ไปที่ `<ConfirmDialog open>` หนึ่ง major แล้วลบใน v5
5. **ออก v4 เป็น `4.0.0-beta.x` บน dist-tag `next` ก่อนไหม?** แนะนำออก beta อย่างน้อย 2 สัปดาห์ เพราะ v4 เปลี่ยนวิธี build และ `exports` map ซึ่งพังได้แบบที่ fixture ของเราไม่ครอบคลุม การ publish เป็นงานของเจ้าของ lib ไม่อยู่ใน phase ไหนของ plan นี้
6. **จะปิด PR ที่เปิดอยู่ (#47, #64, #65, #72, #89, #91) อย่างไร?** แนะนำปิดหลัง v4 beta ออก โดยลิงก์ไปยัง API ที่แทน และให้เครดิตผู้ส่งใน CHANGELOG งานนี้ต้องให้เจ้าของทำเอง plan นี้ไม่ comment หรือปิดอะไร

## 2. API ของ v4

### 2.1 รูปข้อมูลหลัก

ทุกรูปแบบการเรียกใช้ store เดียว ข้อมูลคือรายการ dialog ที่เรียงตามลำดับเปิด

```ts
type DialogId = string & { readonly __brand: 'DialogId' }

type Phase = 'queued' | 'open' | 'closing'

interface Entry {
  id: DialogId
  // R ถูกลบใน store ด้วย cast จุดเดียวใน openDialog เพราะ CustomOptions<R> ใช้ R ในตำแหน่ง parameter
  // ของ render จึง assign เป็น DialogOptions<unknown> ตรง ๆ ไม่ได้ type ของ R กลับมาที่ DialogHandle<R>
  options: DialogOptions<any>
  phase: Phase
  settle: (result: unknown) => void
}

interface StoreState {
  entries: readonly Entry[]
}
```

`phase` เป็น state machine ที่เดินทางเดียว `queued → open → closing → (ลบออก)` ไม่มี boolean ซ้ำซ้อนอย่าง `isOpen` กับ `isClosing` ที่ต้องคอยให้ตรงกัน entry ที่ `phase !== 'queued'` คือ dialog ที่อยู่บนจอ เรียงตามลำดับใน array ตัวสุดท้ายอยู่บนสุด

store อยู่ที่ `globalThis[Symbol.for('react-confirm-alert/v4')]` เพื่อกัน dual package hazard ถ้า bundler โหลดทั้ง ESM และ CJS ของ lib พร้อมกัน (เช่น Next ฝั่ง server ผสม) ทั้งสองชุดจะเห็น store เดียวกัน

### 2.2 Options เป็น discriminated union

```ts
import type {
  ButtonHTMLAttributes,
  ComponentType,
  InputHTMLAttributes,
  KeyboardEvent,
  ReactNode,
} from 'react'

type Strategy = 'stack' | 'queue'

interface BaseOptions {
  title?: ReactNode
  message?: ReactNode
  closeOnEscape?: boolean        // default true
  closeOnClickOutside?: boolean  // default true
  strategy?: Strategy            // default 'stack'
  signal?: AbortSignal           // abort แล้วปิดแบบ dismiss
  className?: string             // ใส่ที่ <dialog>
  overlayClassName?: string      // ชื่อเดิมจาก v3 ใส่ที่ <dialog> เช่นกัน
  onKeyDown?: (event: KeyboardEvent<HTMLDialogElement>, close: () => void) => void
  afterClose?: () => void        // เรียกหลัง animation ปิดจบและ focus คืนแล้ว
}

interface ButtonContext<R> {
  close: (value: R) => void
  dismiss: () => void
  signal: AbortSignal            // abort เมื่อ dialog ถูกปิดจากที่อื่นระหว่างรอ
}

interface DialogButton<R>
  extends Omit<ButtonHTMLAttributes<HTMLButtonElement>, 'onClick' | 'value' | 'children'> {
  label: ReactNode
  value?: R
  variant?: 'primary' | 'secondary' | 'danger'
  // คืน false เพื่อไม่ปิด, คืน Promise เพื่อแสดง loading จนกว่าจะ resolve
  onClick?: (ctx: ButtonContext<R>) => void | false | Promise<void | false>
}

interface AlertOptions extends BaseOptions {
  kind: 'alert'
  okLabel?: ReactNode
}

interface ConfirmOptions extends BaseOptions {
  kind: 'confirm'
  confirmLabel?: ReactNode
  cancelLabel?: ReactNode
  tone?: 'default' | 'danger'    // danger ย้าย focus เริ่มต้นไปที่ปุ่มยกเลิก
  onConfirm?: (ctx: { signal: AbortSignal }) => void | Promise<void>
}

interface PromptOptions extends BaseOptions {
  kind: 'prompt'
  label?: ReactNode
  defaultValue?: string
  inputProps?: Omit<InputHTMLAttributes<HTMLInputElement>, 'value' | 'defaultValue'>
  // คืนข้อความ error เพื่อไม่ปิดและแสดงใต้ช่องกรอก
  validate?: (value: string) => string | null | Promise<string | null>
  submitLabel?: ReactNode
  cancelLabel?: ReactNode
}

interface DialogRenderProps<R> {
  id: DialogId
  titleId: string                 // ผูกกับ aria-labelledby
  descriptionId: string           // ผูกกับ aria-describedby
  title?: ReactNode
  message?: ReactNode
  buttons: readonly DialogButton<R>[]
  busy: boolean
  close: (value: R) => void
  dismiss: () => void
  onClose: () => void             // alias ของ dismiss เพื่อให้ customUI ของ v3 ใช้ได้
}

interface CustomOptions<R> extends BaseOptions {
  kind: 'custom'
  render: ComponentType<DialogRenderProps<R>>
  buttons?: readonly DialogButton<R>[]
}

type DialogOptions<R> = AlertOptions | ConfirmOptions | PromptOptions | CustomOptions<R>

type ResultOf<O> =
  O extends AlertOptions ? void :
  O extends ConfirmOptions ? boolean :
  O extends PromptOptions ? string | null :
  O extends CustomOptions<infer R> ? R | undefined :
  never
```

ผลของการ dismiss (Esc, คลิกนอกกล่อง, `closeAll`, `signal` abort, เปลี่ยน route) กำหนดตาม `kind` ใน type เดียว confirm ได้ `false`, prompt ได้ `null`, custom ได้ `undefined` ผู้ใช้จึงไม่ต้องแยก "กดยกเลิก" กับ "ปิดด้วย Esc" เว้นแต่ใช้ custom แล้วกำหนด `value` เอง

### 2.3 Imperative แบบ Promise

```ts
export function alert(options: string | Omit<AlertOptions, 'kind'>): Promise<void>
export function confirm(options: string | Omit<ConfirmOptions, 'kind'>): Promise<boolean>
export function prompt(options: string | Omit<PromptOptions, 'kind'>): Promise<string | null>

export interface DialogHandle<R> {
  readonly id: DialogId
  readonly result: Promise<R | undefined>
  close(value: R): void
  dismiss(): void
  update(patch: Partial<Omit<CustomOptions<R>, 'kind'>>): void
}
export function openDialog<R = void>(options: Omit<CustomOptions<R>, 'kind'>): DialogHandle<R>

export function closeDialog(id: DialogId): void
export function closeAll(): void
```

ตัวอย่าง

```tsx
if (await confirm({ title: 'ลบไฟล์?', tone: 'danger' })) remove(file)

const name = await prompt({ title: 'ตั้งชื่อ', defaultValue: 'untitled', validate: v => v ? null : 'ต้องกรอก' })

await confirm({
  title: 'บันทึก?',
  onConfirm: async ({ signal }) => { await save({ signal }) }, // ปุ่มแสดง loading จนเสร็จ
})
```

ปุ่ม async ทำงานแบบนี้ เมื่อ `onClick` หรือ `onConfirm` คืน Promise ปุ่มนั้นได้ `aria-busy="true"` และปุ่มอื่น `disabled` ส่วน Esc และคลิกนอกกล่องถูกปิดชั่วคราว Promise resolve แล้ว dialog ปิดด้วย `value` ของปุ่ม ถ้า resolve เป็น `false` dialog ยังเปิดอยู่ ถ้า reject dialog ยังเปิดอยู่ คืนสถานะปุ่ม แล้ว error ส่งต่อไปที่ `console.error` ใน dev เพื่อให้ผู้ใช้จัดการ error ใน `onClick` เอง ถ้า `closeAll` ถูกเรียกระหว่างรอ `signal` จะ abort

### 2.4 Imperative แบบ v3 (ยังใช้ได้)

```ts
export interface ConfirmAlertOptions {
  targetId?: string
  title?: ReactNode
  message?: ReactNode
  buttons?: ReadonlyArray<{ label: ReactNode; className?: string; onClick?: () => void | Promise<void> }
    & Omit<ButtonHTMLAttributes<HTMLButtonElement>, 'onClick' | 'children'>>
  childrenElement?: () => ReactNode
  customUI?: (props: { title?: ReactNode; message?: ReactNode; buttons: ConfirmAlertOptions['buttons']; onClose: () => void }) => ReactNode
  closeOnClickOutside?: boolean
  closeOnEscape?: boolean
  keyCodeForClose?: readonly number[]   // deprecated ใช้ onKeyDown
  willUnmount?: () => void
  afterClose?: () => void
  onClickOutside?: () => void
  onKeypressEscape?: (event: globalThis.KeyboardEvent) => void
  onkeyPress?: (event: globalThis.KeyboardEvent, close: () => void) => void  // deprecated ใช้ onKeyDown
  overlayClassName?: string
}

export function confirmAlert(options: ConfirmAlertOptions): DialogHandle<void>
```

callback สองตัวนี้รับ `KeyboardEvent` ของ DOM ตามที่ v3 ส่ง ไม่ใช่ของ React เพราะ Esc บน `<dialog>` มาเป็น event `cancel` ที่ไม่มีข้อมูลปุ่ม `compat.ts` จึงต้องฟัง `keydown` บน `<dialog>` เพื่อส่ง event จริงให้

`confirmAlert` แปลง options ของ v3 เป็น `CustomOptions<void>` แล้วส่งเข้า store เดียวกับ API ใหม่ ค่าที่คืนเปลี่ยนจาก `void` เป็น `DialogHandle<void>` code ที่ไม่สนค่าคืนยังทำงานเหมือนเดิม `customUI` ถูก render ด้วย `createElement(customUI, props)` ไม่ใช่เรียกเป็นฟังก์ชัน จึงใช้ hook ข้างในได้ ส่วน customUI ของ v3 ที่ไม่มี hook ทำงานเหมือนเดิม

### 2.5 Hook และ host ใน tree ของแอป

```ts
export interface DialogHostProps {
  // ค่านี้เปลี่ยนเมื่อไร dismiss ทุก dialog เช่นส่ง pathname
  dismissKey?: unknown
}
export function DialogHost(props: DialogHostProps): ReactNode

export function useDialog(): {
  alert: typeof alert
  confirm: typeof confirm
  prompt: typeof prompt
  openDialog: typeof openDialog
  closeAll: typeof closeAll
}
```

`<DialogHost>` subscribe store ด้วย `useSyncExternalStore` แล้ว render entry ที่ไม่ใช่ `queued` ตรงตำแหน่งที่วาง host ไม่ต้องใช้ `createPortal` เพราะ `<dialog>` ที่เปิดด้วย `showModal()` ขึ้น top layer เอง ไม่โดน `overflow` หรือ `transform` ของ ancestor บัง ผลคือ dialog อยู่ใน React tree ใต้ provider ทุกตัวที่ครอบ host (Redux, Intl, SWR, theme) ปิด #23 #28 #35 #94

ถ้าไม่มี host ถูก mount ตอนเรียก `confirm()` หรือ `confirmAlert()` lib สร้าง root แยกเองแบบ v3 (lazy และสร้างครั้งเดียว ลบเมื่อ stack ว่าง) ผู้ใช้ v3 จึงไม่ต้องเพิ่ม host แต่จะไม่ได้ context ถ้ามีหลาย host ถูก mount ตัวที่ mount ล่าสุดเป็นตัว render และ dev build เตือนหนึ่งครั้ง

`useDialog()` คืนฟังก์ชันชุดเดียวกับ export ระดับ module (reference คงที่) มีไว้เพื่อให้ code ใน component อ่านแล้วรู้ว่าใช้ dialog และให้ ESLint `react-hooks` จับ dependency ได้ ไม่ได้ผูก store แยกต่อ host

### 2.7 customUI ที่อ่าน state ล่าสุด (#63, #66)

มีสามทาง เรียงจากแนะนำมากไปน้อย

### 2.8 ซ้อนกัน, คิว, ปิดทั้งหมด, เปลี่ยน route

### 2.9 สภาพแวดล้อม

- **SSR** import แล้วไม่แตะ `window` หรือ `document` ที่ระดับ module `DialogHost` render `null` บน server เพราะ store ว่าง จึงไม่มี hydration mismatch ถ้าเรียก `confirm()` บน server Promise จะ reject ด้วย `Error('react-confirm-alert: dialogs need a browser')`
- **Next app router** ไฟล์ entry ขึ้นต้นด้วย `'use client'` (ต้องใส่ผ่าน `output.banner` เพราะ Rollup ตัด directive ระดับ module ออกตอนรวมไฟล์) ผู้ใช้ import `DialogHost` ใน `layout.tsx` ที่เป็น server component ได้
- **React 18 และ 19** peer `react` และ `react-dom` เป็น `^18.0.0 || ^19.0.0` ใช้แค่ `useSyncExternalStore`, `useId`, `useEffect`, `createRoot` ไม่ใช้ `propTypes`, `defaultProps` บน function component, `forwardRef`, `findDOMNode` หรือ `element.ref` ซึ่ง 19 ลบหรือ deprecate แล้ว effect ที่เรียก `showModal()` ต้องเช็ก `dialog.open` ก่อนเรียก และ cleanup ต้องเรียก `close()` เพื่อให้ StrictMode ที่รัน effect สองรอบไม่ throw `InvalidStateError`

- **Test และ mock (#48)** ฟังก์ชันทุกตัวคืน Promise จึง mock ได้ตรง ๆ

## 3. การตัดสินใจหลัก

### 3.1 ใช้ `<dialog>` แบบ native และ top layer

**ใช้** เพราะแก้ปัญหาที่ v3 เขียนเองแล้วพังได้ทีเดียวสามข้อ top layer ไม่ต้องแข่ง z-index (#31) `showModal()` ทำให้พื้นหลัง inert และย้าย focus เข้า dialog (#29) และ `::backdrop` แทน overlay div กับ SVG blur ที่ผูกกับ `body.children[0]` (#77)

สิ่งที่ต้องเขียนเองเพราะ browser ไม่ทำให้

- **คลิกนอกกล่อง** คลิกที่ backdrop ให้ `event.target` เป็นตัว `<dialog>` lib จึงให้เนื้อหาอยู่ใน wrapper ที่เต็มกล่อง และปิดเมื่อทั้ง `pointerdown` และ `click` มี target เป็น `<dialog>` เท่านั้น การจำ target ของ `pointerdown` คือสิ่งที่แก้ #92
- **Esc เมื่อ `closeOnEscape: false`** เรียก `preventDefault()` ใน event `cancel` ความเสี่ยงคือ Chrome อาจยอมให้ Esc ซ้ำปิด dialog แม้ถูก `preventDefault` (พฤติกรรมของ CloseWatcher) นี่เป็นสิ่งที่จำได้ ยังไม่ได้วัด P2 ต้องมี test ใน Chromium ถ้าเกิดจริงให้ฟัง `close` แล้ว `showModal()` ใหม่
- **ไม่ใช้ attribute `closedby`** เพราะ Safari ยังไม่รองรับ
- **jsdom** fallback ตามข้อ 2.9

### 3.2 root แยกหรือ portal ใน provider

**ใช้ทั้งสองแบบ แต่เป็น render path เดียว** component ที่ render entry มีตัวเดียว (`DialogStack`) ถ้ามี `<DialogHost>` ถูก mount `DialogStack` อยู่ใน tree ของแอป ถ้าไม่มี lib สร้าง root แยกที่ render `DialogStack` ตัวเดียวกัน ไม่มีการใช้ `createPortal` เพราะ top layer ทำให้ไม่ต้องย้าย DOM

เหตุผลที่ไม่เลือกแบบเดียว ถ้าบังคับ host ผู้ใช้ v3 ทุกคนต้องแก้ code ตอนอัปเกรด ถ้าใช้ root แยกอย่างเดียว ปัญหา context (#23 #28 #35 #94) แก้ไม่ได้

### 3.3 Motion ที่เคารพ `prefers-reduced-motion`

- เปิดด้วย CSS keyframe บน `dialog[data-state='open']` และ `::backdrop` ตัด delay 0.2s ของ v3 ออก ระยะเวลาเป็น `--rca-duration` (ค่าเริ่มต้น 160ms)
- ปิดด้วยการตั้ง `phase: 'closing'` ซึ่ง render เป็น `data-state='closing'` แล้วรอ animation ของตัว `<dialog>` และ `::backdrop` จบก่อนเรียก `dialog.close()` และลบ entry ใช้ `dialog.getAnimations({ subtree: true })` แล้วกรองเหลือเฉพาะตัวที่ `effect.target === dialog` (ครอบ `::backdrop` ด้วย ซึ่งเรียกแบบไม่มี `subtree` จะไม่ได้) ห้ามรอ animation ของลูก เพราะ animation แบบ infinite เช่น spinner ของปุ่ม busy ไม่มีวันจบ ไม่ใช้ `setTimeout` เดาเวลา จึงไม่ค้างถ้าผู้ใช้ override CSS
- `@media (prefers-reduced-motion: reduce)` ตั้ง `animation: none` เมื่อไม่มี animation `getAnimations()` คืน array ว่าง dialog ปิดทันที ตรรกะ JS ไม่ต้องเช็ก media query เอง
- ไม่ใช้ `@starting-style` กับ `transition-behavior: allow-discrete` เป็นทางหลัก เพราะ Firefox เพิ่งรองรับ (129) และ exit transition ของ top layer ยังต่างกันในแต่ละ browser keyframe ทำงานเหมือนกันทุกที่

### 3.4 Focus และ a11y

- `role="alertdialog"` สำหรับ alert และ confirm, `role="dialog"` สำหรับ prompt และ custom
- `aria-labelledby` และ `aria-describedby` ผูกกับ id จาก `useId()` ส่งให้ custom ผ่าน `titleId` และ `descriptionId`
- focus เริ่มต้น confirm ปกติไปที่ปุ่มยืนยัน, `tone: 'danger'` ไปที่ปุ่มยกเลิก, prompt ไปที่ช่องกรอก, custom ไปที่ element ที่มี `autoFocus` ตัวแรก ถ้าไม่มีให้ browser เลือก
- คืน focus ไปที่ element ที่ focus ก่อนเปิด หลังปิด ถ้า element นั้นยังอยู่ใน DOM (ทำเองแม้ spec ใหม่จะทำให้ เพราะ fallback ใน jsdom ไม่ทำ)
- prompt ใช้ `<form method="dialog">` กด Enter แล้ว submit โดย handler ต้อง `preventDefault()` เสมอ ไม่อย่างนั้น browser ปิด dialog เองทันที ข้าม `validate` และ animation ปิด, error จาก `validate` ผูกด้วย `aria-invalid` และ `aria-describedby`
- scroll lock ใช้ class `react-confirm-alert-body-element` บน `body` แบบ v3 (ชื่อเดิมเพื่อให้ CSS ของผู้ใช้ยังใช้ได้) ตั้งเมื่อมี entry ที่ `open` อย่างน้อยหนึ่งตัว ลบเมื่อไม่มี คำนวณจาก store ไม่ใช่ add/remove ตามแต่ละ dialog จึงไม่หลุดเมื่อซ้อนกัน

### 3.5 Zero runtime dependency

`dependencies` ว่าง มีแค่ `peerDependencies` ของ `react` และ `react-dom` ลบ `prop-types` (ต้นเหตุ #85, และ React 19 ไม่อ่าน `propTypes` แล้ว) TypeScript ทำหน้าที่ตรวจ props แทน devDependency ที่เพิ่มจะระบุในแต่ละ phase

### 3.7 TypeScript strict แบบ discriminated union

- `tsconfig` เปิด `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`

## 4. ย้ายจาก v3 ไป v4

### 4.1 สิ่งที่ใช้ได้เหมือนเดิมโดยไม่ต้องแก้

| v3 | v4 |
|---|---|
| `import { confirmAlert } from 'react-confirm-alert'` | ใช้ได้ |
| `import 'react-confirm-alert/src/react-confirm-alert.css'` | ใช้ได้ (alias ใน `exports`) |
| options ทุกตัวในข้อ 2.4 | ใช้ได้ `keyCodeForClose` และ `onkeyPress` เตือน deprecate ใน dev |
| `customUI: ({ onClose }) => ...` | ใช้ได้ และตอนนี้ใช้ hook ข้างในได้ |
| class `react-confirm-alert-overlay`, `react-confirm-alert`, `react-confirm-alert-body`, `react-confirm-alert-button-group`, `react-confirm-alert-body-element` | คงชื่อเดิมบน element ที่ใกล้เคียงที่สุด `-overlay` อยู่บน `<dialog>` |
| `targetId` | ใช้ได้ (root แยกถูกสร้างใน element นั้น) |

### 4.2 สิ่งที่เปลี่ยนและต้องแก้

| v3 | v4 | สิ่งที่ผู้ใช้ต้องทำ |
|---|---|---|
| React 18 ขึ้นไปแต่ peer เขียน `react-dom >=10` | peer `^18 \|\| ^19` ทั้งคู่ | ไม่มีถ้าใช้ 18/19 |
| overlay เป็น `div` z-index 99 | `<dialog>` ใน top layer | CSS ที่ override `z-index` หรือ `position` ของ `.react-confirm-alert-overlay` ไม่มีผลแล้ว ลบทิ้งได้ |
| blur ผ่าน `.react-confirm-alert-blur` บน `body.children[0]` และ `<svg id="react-confirm-alert-firm-svg">` | `::backdrop { backdrop-filter: blur(var(--rca-blur)) }` | CSS ที่อ้าง `.react-confirm-alert-blur` ต้องย้ายไปตั้ง `--rca-blur` |
| เรียกซ้อนแล้วตัวเก่าหาย | ซ้อนกัน (stack) | ถ้าเคยพึ่งให้ตัวใหม่แทนตัวเก่า เรียก `closeAll()` ก่อน |
| `confirmAlert` คืน `void` | คืน `DialogHandle<void>` | ไม่มี |
| default export class ที่ใช้ตรง ๆ ไม่ได้ | alias ไป `ConfirmDialog` (ตามคำถามข้อ 4) | เปลี่ยนไปใช้ `<ConfirmDialog open>` |
| fade-in delay 0.2s | ไม่มี delay | test ที่รอ 700ms รอน้อยลงได้ |
| browser ที่ไม่มี `showModal` | ไม่รองรับ | ตามคำถามข้อ 3 |

### 4.3 ทางย้ายที่แนะนำ

1. อัปเกรดแล้วไม่ต้องแก้อะไร `confirmAlert` เดิมทำงาน
2. วาง `<DialogHost />` ใต้ provider ของแอป (Redux, Intl, theme) dialog ทุกตัวจะได้ context ทันที
3. ย้ายจุดเรียกทีละจุดจาก `confirmAlert({ buttons: [...] })` เป็น `if (await confirm(...))`
4. dialog ที่ต้องอ่าน state ของ component ย้ายไปเป็น `<Dialog open>`

MIGRATION.md (P6) จะมีตัวอย่างก่อนและหลังของแต่ละข้อ
