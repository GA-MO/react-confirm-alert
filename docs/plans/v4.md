0. **ออกเป็น 3.1.0 (minor) แทน 4.0.0 ไหม?** แนะนำออกเป็น **3.1.0** แล้วค่อยออก 4.0.0 ทีหลังเป็นรุ่นเล็กที่เปลี่ยนค่าเริ่มต้นอย่างเดียว เหตุผลอยู่ในข้อ 4.3 สรุปสั้น ๆ คือ plan นี้ออกแบบให้ `confirmAlert` ค่าเริ่มต้นได้ DOM, class, path ของ CSS, จังหวะการปิด และ type แบบเดียวกับ v3 สิ่งที่เปลี่ยนโดยผู้ใช้ไม่ได้เลือกเหลือแค่ bug fix (ตาราง 4.2) ส่วน API ใหม่ทั้งหมดเป็นของที่เพิ่มเข้ามา ผู้ใช้ที่ติดตั้งด้วย `^3` (ค่าที่ `npm install` เขียนให้) จะได้ fix ของ #77 #82 #85 #92 เองโดยไม่ต้องแก้อะไร ถ้าออกเป็น 4.0.0 ผู้ใช้ต้องอัปเกรดเอง และส่วนใหญ่จะค้างอยู่ที่ 3.0.6 ราคาที่ต้องจ่ายคือ bug ใน 3.1.0 จะไปถึงทุกคนทันที plan จึงบังคับ beta บน `next` อย่างน้อย 2 สัปดาห์ (P7) และมี contract test ของ v3 ตั้งแต่ P0 ถ้าเลือก 4.0.0 แทน ให้อ่าน "3.1.0" ในไฟล์นี้เป็น "4.0.0" และรวม P9 เข้าไปใน release เดียวกัน ในไฟล์นี้คำว่า "v4" ยังหมายถึงชุดงานทั้งหมด ไม่ได้หมายถึงเลขเวอร์ชัน
1. **เรียกซ้อนตอนที่มี dialog เปิดอยู่ ค่าเริ่มต้นของ API ใหม่เป็นซ้อน (stack) หรือต่อคิว (queue)?** `confirmAlert` ใช้ `replace` แบบ v3 ไปจนถึง 4.0.0 เพื่อไม่ให้พฤติกรรมเดิมเปลี่ยน (ตาราง 4.2) ส่วน API ใหม่แนะนำ `stack` เพราะตรงกับ #46/#47 ซึ่งเป็นกรณีที่คนเจอบ่อยกว่า (เปิด dialog จากใน dialog) ส่วน #72 ใช้ `strategy: 'queue'` ต่อครั้งได้ ถ้าเลือก queue เป็นค่าเริ่มต้น dialog ที่เปิดจากในอีก dialog จะค้างรอจนตัวแม่ปิด ซึ่งคือ deadlock ในกรณี nested
2. **หน้าตาเริ่มต้นของ 4.0.0 จะออกแบบใหม่ไหม?** 3.1.0 คงทุกค่าของ v3 (overlay สีขาว 90%, ปุ่มดำ, กว้าง 400px, fade-in 0.5s หลัง delay 0.2s, blur ผ่าน class บน `body.children[0]`) เพราะเปลี่ยนแล้วนับเป็นการเปลี่ยนที่ผู้ใช้ไม่ได้เลือก ทุกค่าเป็น CSS variable แล้ว คำถามคือ 4.0.0 จะตัด delay และย้าย blur ไป `::backdrop` ไหม แนะนำทำทั้งสองอย่างใน 4.0.0 นี่เป็นเรื่องรสนิยมของเจ้าของ lib ทดลองตัดสินไม่ได้
3. **browser ที่ไม่มี `<dialog>.showModal()` (ก่อน Safari 15.4, Firefox 98) ได้อะไร?** ไม่ต้องตัด เพราะ `modal: false` (ค่าเริ่มต้นของ `confirmAlert`) render เป็น `div` overlay แบบ v3 อยู่แล้ว lib ใช้ทางนั้นเองเมื่อไม่มี `showModal` (รวม jsdom) จึงไม่ต้องมี polyfill browser เก่าได้พฤติกรรมเท่า v3 คือไม่มี inert และไม่มี top layer คำถามที่เหลือคือ ยอมให้ API ใหม่ใน browser เก่าทำงานแบบนี้ไหม แนะนำยอม
4. **default export `ReactConfirmAlert` (class component) จะเก็บไว้ไหม?** ใน v3 ใช้แบบ declarative ได้จริง (`{show && <ReactConfirmAlert buttons={[{ label: 'OK', onClick: () => setShow(false) }]} />}`) เพราะ `close()` ไม่พังเมื่อไม่มี root (`src/index.js:199-204`) แนะนำเก็บเป็น class เล็ก ๆ ที่ render frame แบบ `div` ด้วย props ชุดเดิม ไม่เตือน deprecate ตอน runtime ใส่แค่ JSDoc `@deprecated` และลบใน v5
5. **beta บน dist-tag `next` นานเท่าไร?** แนะนำอย่างน้อย 2 สัปดาห์ และไม่มี issue ใหม่ที่เป็น regression ของ v3 ก่อนเลื่อนเป็น `latest` (P7) ถ้าเลือก 3.1.0 ข้อนี้สำคัญกว่าปกติ เพราะ `latest` ของ 3.x ไปถึงผู้ใช้ `^3` ทุกคนทันที
6. **merge PR #91 เข้า `master` ก่อนเริ่ม P1 ไหม?** แนะนำ merge เพราะแก้ถูกและเล็ก (เพิ่ม `afterClose` ใน type) ผู้ส่งได้เครดิตใน git history โดยตรง ส่วนจะออก 3.0.7 ให้ผู้ใช้ v3 ด้วยหรือไม่ แนะนำออกเฉพาะเมื่อ v4 stable ยังห่างเกิน 1 เดือน PR อื่นอีก 5 ตัวแนะนำปิดพร้อมเครดิต ดูภาคผนวก A
7. **ตอบและปิด issue/PR ตอนออก beta หรือ stable?** แนะนำตอน stable เพราะข้อความตอบเขียนว่า "แก้แล้วใน {version}" ผู้ใช้ควร `npm i react-confirm-alert` แล้วได้ของที่แก้ทันที ถ้าปิดตอน beta ต้องบอกให้ติดตั้ง `@next` ซึ่งคนอ่านทีหลังจะสับสน P8 ทำงานนี้ และเจ้าของกดส่งเอง
8. **เว็บเอกสารอยู่ที่ไหน?** แนะนำ `https://ga-mo.github.io/react-confirm-alert/` (GitHub Pages ของ repo เดิม) ต้องเปลี่ยน Settings → Pages → Source เป็น "GitHub Actions" ซึ่งเจ้าของต้องกดเอง ลิงก์ demo เดิม `/demo/` จะ redirect ไปหน้าแรก ถ้าอยากใช้ custom domain ต้องตั้ง DNS และ `basePath` จะเป็นค่าว่าง
9. **CSS เริ่มต้นจะเปลี่ยนเป็นโหมดมืดตาม `prefers-color-scheme` เองไหม?** แนะนำไม่ เพราะแอปของผู้ใช้ v3 ส่วนใหญ่ไม่มีโหมดมืด ถ้าตามระบบเอง ผู้ใช้ที่ตั้ง OS เป็นโหมดมืดจะเห็น dialog สีเข้มบนแอปสีขาวทันทีที่อัปเกรด v4 ให้ชุดตัวแปรโหมดมืดเป็นตัวอย่างในเอกสารแทน ผู้ใช้ copy ไปใส่ใต้ selector ของตัวเองได้

## 2. API ของ v4

### 2.1 รูปข้อมูลหลัก

ทุกรูปแบบการเรียกใช้ store เดียว ข้อมูลคือรายการ dialog ที่เรียงตามลำดับเปิด

```ts
type DialogId = string & { readonly __brand: 'DialogId' }

type Phase = 'queued' | 'open' | 'closing'

interface Entry {
  id: DialogId
  // R ถูกลบใน store ด้วย cast จุดเดียวใน openDialog เพราะ CustomOptions<R> ใช้ R ในตำแหน่ง parameter
  // ของ render จึง assign เป็น DialogOptions<unknown> ตรง ๆ ไม่ได้ type ของ R กลับมาที่ DialogHandle<R>
  options: DialogOptions<any>
  phase: Phase
  settle: (result: unknown) => void
}

interface StoreState {
  entries: readonly Entry[]
}
```

`phase` เป็น state machine ที่เดินทางเดียว `queued → open → closing → (ลบออก)` ไม่มี boolean ซ้ำซ้อนอย่าง `isOpen` กับ `isClosing` ที่ต้องคอยให้ตรงกัน entry ที่ `phase !== 'queued'` คือ dialog ที่อยู่บนจอ เรียงตามลำดับใน array ตัวสุดท้ายอยู่บนสุด

store อยู่ที่ `globalThis[Symbol.for('react-confirm-alert/v4')]` เพื่อกัน dual package hazard ถ้า bundler โหลดทั้ง ESM และ CJS ของ lib พร้อมกัน (เช่น Next ฝั่ง server ผสม) ทั้งสองชุดจะเห็น store เดียวกัน

### 2.2 Options เป็น discriminated union

```ts
import type {
  ButtonHTMLAttributes,
  ComponentType,
  InputHTMLAttributes,
  KeyboardEvent,
  ReactNode,
} from 'react'

type Strategy = 'stack' | 'queue' | 'replace'   // replace ปิดตัวที่เปิดอยู่ก่อน (ค่าเริ่มต้นของ confirmAlert)

interface BaseOptions {
  title?: ReactNode
  message?: ReactNode
  closeOnEscape?: boolean        // default true
  closeOnClickOutside?: boolean  // default true
  strategy?: Strategy            // default 'stack' (confirmAlert: 'replace')
  modal?: boolean                // default true (confirmAlert: false) ดูข้อ 3.1
  signal?: AbortSignal           // abort แล้วปิดแบบ dismiss
  unstyled?: boolean             // ดูข้อ 2.10
  classNames?: DialogClassNames  // ดูข้อ 2.10 ต่อท้าย classNames จาก configureDialogs ไม่ได้แทนที่
  onKeyDown?: (event: KeyboardEvent<HTMLDialogElement>, close: () => void) => void
  afterClose?: () => void        // เรียกหลัง animation ปิดจบและ focus คืนแล้ว
}

interface ButtonContext<R> {
  close: (value: R) => void
  dismiss: () => void
  signal: AbortSignal            // abort เมื่อ dialog ถูกปิดจากที่อื่นระหว่างรอ
}

interface DialogButton<R>
  extends Omit<ButtonHTMLAttributes<HTMLButtonElement>, 'onClick' | 'value' | 'children'> {
  label: ReactNode
  value?: R
  variant?: 'primary' | 'secondary' | 'danger'
  // คืน false เพื่อไม่ปิด, คืน Promise เพื่อแสดง loading จนกว่าจะ resolve
  onClick?: (ctx: ButtonContext<R>) => void | false | Promise<void | false>
}

interface AlertOptions extends BaseOptions {
  kind: 'alert'
  okLabel?: ReactNode
}

interface ConfirmOptions extends BaseOptions {
  kind: 'confirm'
  confirmLabel?: ReactNode
  cancelLabel?: ReactNode
  tone?: 'default' | 'danger'    // danger ย้าย focus เริ่มต้นไปที่ปุ่มยกเลิก
  onConfirm?: (ctx: { signal: AbortSignal }) => void | Promise<void>
}

interface PromptOptions extends BaseOptions {
  kind: 'prompt'
  label?: ReactNode
  defaultValue?: string
  inputProps?: Omit<InputHTMLAttributes<HTMLInputElement>, 'value' | 'defaultValue'>
  // คืนข้อความ error เพื่อไม่ปิดและแสดงใต้ช่องกรอก
  validate?: (value: string) => string | null | Promise<string | null>
  submitLabel?: ReactNode
  cancelLabel?: ReactNode
}

interface DialogRenderProps<R> {
  id: DialogId
  titleId: string                 // ผูกกับ aria-labelledby
  descriptionId: string           // ผูกกับ aria-describedby
  title?: ReactNode
  message?: ReactNode
  buttons: readonly DialogButton<R>[]
  busy: boolean
  close: (value: R) => void
  dismiss: () => void
  onClose: () => void             // alias ของ dismiss เพื่อให้ customUI ของ v3 ใช้ได้
}

interface CustomOptions<R> extends BaseOptions {
  kind: 'custom'
  render: ComponentType<DialogRenderProps<R>>
  buttons?: readonly DialogButton<R>[]
}

type DialogOptions<R> = AlertOptions | ConfirmOptions | PromptOptions | CustomOptions<R>

type ResultOf<O> =
  O extends AlertOptions ? void :
  O extends ConfirmOptions ? boolean :
  O extends PromptOptions ? string | null :
  O extends CustomOptions<infer R> ? R | undefined :
  never
```

ผลของการ dismiss (Esc, คลิกนอกกล่อง, `closeAll`, `signal` abort, เปลี่ยน route) กำหนดตาม `kind` ใน type เดียว confirm ได้ `false`, prompt ได้ `null`, custom ได้ `undefined` ผู้ใช้จึงไม่ต้องแยก "กดยกเลิก" กับ "ปิดด้วย Esc" เว้นแต่ใช้ custom แล้วกำหนด `value` เอง

### 2.3 Imperative แบบ Promise

```ts
export function alert(options: string | Omit<AlertOptions, 'kind'>): Promise<void>
export function confirm(options: string | Omit<ConfirmOptions, 'kind'>): Promise<boolean>
export function prompt(options: string | Omit<PromptOptions, 'kind'>): Promise<string | null>

export interface DialogHandle<R> {
  readonly id: DialogId
  readonly result: Promise<R | undefined>
  close(value: R): void
  dismiss(): void
  update(patch: Partial<Omit<CustomOptions<R>, 'kind'>>): void
}
export function openDialog<R = void>(options: Omit<CustomOptions<R>, 'kind'>): DialogHandle<R>

export function closeDialog(id: DialogId): void
export function closeAll(): void
```

ตัวอย่าง

```tsx
if (await confirm({ title: 'ลบไฟล์?', tone: 'danger' })) remove(file)

const name = await prompt({ title: 'ตั้งชื่อ', defaultValue: 'untitled', validate: v => v ? null : 'ต้องกรอก' })

await confirm({
  title: 'บันทึก?',
  onConfirm: async ({ signal }) => { await save({ signal }) }, // ปุ่มแสดง loading จนเสร็จ
})
```

ปุ่ม async ทำงานแบบนี้ เมื่อ `onClick` หรือ `onConfirm` คืน Promise ปุ่มนั้นได้ `aria-busy="true"` และปุ่มอื่น `disabled` ส่วน Esc และคลิกนอกกล่องถูกปิดชั่วคราว Promise resolve แล้ว dialog ปิดด้วย `value` ของปุ่ม ถ้า resolve เป็น `false` dialog ยังเปิดอยู่ ถ้า reject dialog ยังเปิดอยู่ คืนสถานะปุ่ม แล้ว error ส่งต่อไปที่ `console.error` ใน dev เพื่อให้ผู้ใช้จัดการ error ใน `onClick` เอง ถ้า `closeAll` ถูกเรียกระหว่างรอ `signal` จะ abort

### 2.4 Imperative แบบ v3 (ยังใช้ได้เหมือนเดิม)

type ของ API v3 คงชื่อและรูปเดิมทุกตัว เพิ่มได้อย่างเดียว ไม่แคบลง ไม่เปลี่ยนชนิดของค่าที่คืน

```ts
export interface ReactConfirmAlertProps {
  targetId?: string
  title?: string
  message?: string
  buttons?: Array<{ label: string; className?: string } & ButtonHTMLAttributes<HTMLButtonElement>>
  childrenElement?: () => ReactNode
  customUI?: (customUiOptions: {
    title: string
    message: string
    buttons: NonNullable<ReactConfirmAlertProps['buttons']>   // v3 ส่งค่านี้อยู่แล้วแต่ type ไม่มี
    onClose: () => void
  }) => ReactNode
  closeOnClickOutside?: boolean
  closeOnEscape?: boolean
  /** @deprecated ใช้ onKeyDown กับ API ใหม่ */
  keyCodeForClose?: Array<number>
  willUnmount?: () => void
  afterClose?: () => void                                  // #90 #91
  onClickOutside?: () => void
  onKeypressEscape?: (event: globalThis.KeyboardEvent) => void
  /** @deprecated ใช้ onKeyDown กับ API ใหม่ */
  onkeyPress?: (event: globalThis.KeyboardEvent, close: () => void) => void   // #84 #89
  overlayClassName?: string
  // ของใหม่ที่เลือกใช้ได้ ค่าเริ่มต้นคือพฤติกรรม v3
  modal?: boolean              // default false
  strategy?: Strategy          // default 'replace'
  unstyled?: boolean
  classNames?: DialogClassNames
}
export type ConfirmAlertOptions = ReactConfirmAlertProps

export function confirmAlert(options: ReactConfirmAlertProps): void

/** @deprecated ใช้ <ConfirmDialog open> */
export default class ReactConfirmAlert extends Component<ReactConfirmAlertProps> {}
```

พฤติกรรมที่ `confirmAlert` ต้องคงไว้ (P0 เขียนเป็น contract test ทุกข้อ)

- คืน `undefined` ไม่ใช่ handle เพราะ test ที่ `jest.spyOn(mod, 'confirmAlert').mockImplementation(() => {})` จะ compile ไม่ผ่านถ้าชนิดค่าคืนเปลี่ยน คนที่ต้องการ handle ใช้ `openDialog`
- `role="dialog"` บน overlay (API ใหม่ใช้ `alertdialog` กับ alert และ confirm) และ focus ย้ายไปที่ `panel` (`tabIndex={-1}`) ไม่ใช่ปุ่ม เพื่อไม่ให้ Enter หรือ Space กดปุ่มยืนยันโดยไม่ตั้งใจ (B14)
- message เป็น text node เปล่าแบบ v3 ไม่มี wrapper และไม่มี `white-space: pre-line` (B22)
- DOM แบบเดิม `#react-confirm-alert` (หรือ `targetId`) > `div.react-confirm-alert-overlay` > `div.react-confirm-alert` > `div.react-confirm-alert-body` > `h1`, message, `childrenElement()`, `div.react-confirm-alert-button-group` > `button` ที่ spread props ของปุ่มทุกตัวแบบ v3 ส่วนที่เพิ่มคือ attribute (`role`, `aria-*`, `data-*`) เท่านั้น
- ปุ่มเรียก `onClick()` โดยไม่มี argument แล้วปิดทันทีในจังหวะเดียวกัน ไม่รอ Promise แม้ `onClick` จะเป็น `async` (ถ้ารอ dialog จะค้างเปิดระหว่างรอ และค้างถาวรถ้า reject ซึ่งต่างจาก v3)
- ลำดับตอนปิดคือ `willUnmount` แล้ว `afterClose` และเกิดก่อนที่ event handler ของการคลิกจะจบ (ไม่มี animation ขาปิดในค่าเริ่มต้น จึงไม่มีอะไรให้รอ)
- เรียกซ้ำตอนที่ยังเปิดอยู่ ตัวใหม่แทนตัวเก่า (`strategy: 'replace'`) แต่ไม่มี error ของ `createRoot` ใน v3 ตัวเก่าไม่เคยถูก unmount callback ของมันจึงไม่เคยถูกเรียก และ listener `keydown` ของมันค้าง ใน 3.1.0 ตัวเก่าได้ `willUnmount` กับ `afterClose` หนึ่งครั้ง (B21)
- `keydown` ฟังที่ `document` แบบเดิม `keyCodeForClose`, `onkeyPress`, Esc ทำงานเหมือนเดิม (`onkeyPress` ได้ argument เพิ่ม ซึ่งฟังก์ชันเดิมที่ไม่รับ argument ไม่รู้สึก)
- คลิก overlay เรียก `onClickOutside` แล้ว `stopPropagation` แบบ #78
- `body` ได้ class `react-confirm-alert-body-element` และ `body.children[0]` ได้ `react-confirm-alert-blur` เมื่อ lib เป็นคนสร้าง container (ไม่มี `targetId` และไม่มี `#react-confirm-alert` อยู่ก่อน) ทุกครั้งที่เปิด ไม่ใช่แค่ครั้งแรก (#77) และลบ container เฉพาะตัวที่ lib สร้าง
- ไม่มี `console.warn` ตอน runtime สำหรับ option ที่ deprecate เพราะชุด test ที่ตั้งให้ล้มเมื่อมี warning (เช่น `jest-fail-on-console`) จะพัง ใช้ JSDoc `@deprecated` แทน

`confirmAlert` แปลง options เป็น `CustomOptions<void>` ที่มี `modal: false`, `strategy: 'replace'` และตัวแปลงปุ่มแบบ v3 แล้วส่งเข้า store เดียวกับ API ใหม่ `customUI` ถูก render ด้วย `createElement(customUI, props)` ไม่ใช่เรียกเป็นฟังก์ชัน จึงใช้ hook ข้างในได้ customUI ของ v3 ที่ไม่มี hook ได้ผลเหมือนเดิม เพราะ v3 ก็เรียกแบบไม่มี `this` เช่นกัน (`src/index.js:107`)

callback ของคีย์บอร์ดรับ `KeyboardEvent` ของ DOM ตามที่ v3 ส่ง ไม่ใช่ของ React เมื่อผู้ใช้เลือก `modal: true` Esc จะมาเป็น event `cancel` ที่ไม่มีข้อมูลปุ่ม `compat.ts` จึงฟัง `keydown` ที่ `document` ทั้งสองโหมด

ผู้ใช้ v3 ที่อยากได้พฤติกรรมใหม่ทั้งหมดโดยไม่แก้ทุกจุดเรียก ตั้งครั้งเดียวได้

```ts
configureDialogs({ confirmAlert: { modal: true, strategy: 'stack' } })
```

### 2.5 Hook และ host ใน tree ของแอป

```ts
export interface DialogHostProps {
  // ค่านี้เปลี่ยนเมื่อไร dismiss ทุก dialog เช่นส่ง pathname
  dismissKey?: unknown
}
export function DialogHost(props: DialogHostProps): ReactNode

export function useDialog(): {
  alert: typeof alert
  confirm: typeof confirm
  prompt: typeof prompt
  openDialog: typeof openDialog
```

`<DialogHost>` subscribe store ด้วย `useSyncExternalStore` แล้ว render entry ที่ไม่ใช่ `queued` ตรงตำแหน่งที่วาง host ไม่ต้องใช้ `createPortal` เพราะ `<dialog>` ที่เปิดด้วย `showModal()` ขึ้น top layer เอง ไม่โดน `overflow` หรือ `transform` ของ ancestor บัง ผลคือ dialog อยู่ใน React tree ใต้ provider ทุกตัวที่ครอบ host (Redux, Intl, SWR, theme) ปิด #23 #28 #35 #94

ถ้าไม่มี host ถูก mount ตอนเรียก `confirm()` หรือ `confirmAlert()` lib สร้าง root แยกเองแบบ v3 (lazy และสร้างครั้งเดียว ลบเมื่อ stack ว่าง) ผู้ใช้ v3 จึงไม่ต้องเพิ่ม host แต่จะไม่ได้ context ถ้ามีหลาย host ถูก mount ตัวที่ mount ล่าสุดเป็นตัว render และ dev build เตือนหนึ่งครั้ง

`useDialog()` คืนฟังก์ชันชุดเดียวกับ export ระดับ module (reference คงที่) มีไว้เพื่อให้ code ใน component อ่านแล้วรู้ว่าใช้ dialog และให้ ESLint `react-hooks` จับ dependency ได้ ไม่ได้ผูก store แยกต่อ host

### 2.6 Component แบบ declarative

```ts
interface DeclarativeBase {
  open: boolean
  onOpenChange: (open: boolean) => void
}

export type ConfirmDialogProps =
  | (DeclarativeBase & Omit<AlertOptions, 'signal' | 'strategy'>)
  | (DeclarativeBase & Omit<ConfirmOptions, 'signal' | 'strategy'>)
  | (DeclarativeBase & Omit<PromptOptions, 'signal' | 'strategy'> & { onSubmit: (value: string) => void | Promise<void> })

export function ConfirmDialog(props: ConfirmDialogProps): ReactNode

export interface DialogProps extends DeclarativeBase, Omit<BaseOptions, 'signal' | 'strategy' | 'title' | 'message'> {
  children: ReactNode
  'aria-labelledby'?: string
  'aria-describedby'?: string

```

component แบบ declarative render `<dialog>` ตรงที่วาง ไม่ผ่าน store children จึงอ่าน state ล่าสุดของ component แม่ได้ทันที นี่คือคำตอบหลักของ #63 และ #66

```tsx
const [open, setOpen] = useState(false)
const [note, setNote] = useState('')
<Dialog open={open} onOpenChange={setOpen} aria-labelledby="t">
  <h2 id="t">แก้โน้ต</h2>
  <textarea value={note} onChange={e => setNote(e.target.value)} />
  <button disabled={!note} onClick={() => setOpen(false)}>บันทึก</button>
</Dialog>
```

### 2.7 customUI ที่อ่าน state ล่าสุด (#63, #66)

มีสามทาง เรียงจากแนะนำมากไปน้อย

1. ใช้ `<Dialog open>` แบบ 2.6 state อยู่ที่ component แม่ ไม่มีปัญหา snapshot
2. ใช้ `openDialog({ render: EditNote })` แล้วให้ state อยู่ใน `EditNote` เอง เพราะ v4 render เป็น component จึงมี state และ hook ของตัวเอง ค่าที่ต้องส่งกลับใช้ `close(value)`
3. ใช้ `handle.update({ ... })` ส่งค่าใหม่จากภายนอกเข้า dialog ที่เปิดอยู่ เหมาะกับการ push ความคืบหน้า ไม่เหมาะเป็นวิธีหลัก

### 2.8 ซ้อนกัน, คิว, ปิดทั้งหมด, เปลี่ยน route

- `strategy: 'stack'` (default) เปิดทับตัวที่เปิดอยู่ Esc ปิดเฉพาะตัวบนสุด เพราะ browser ส่ง `cancel` ให้ dialog บนสุดของ top layer
- `strategy: 'queue'` เข้า `phase: 'queued'` แล้วเปิดเมื่อไม่มี entry ที่ `open` หรือ `closing` เหลือ
- `closeAll()` dismiss ทุก entry รวมตัวที่อยู่ในคิว Promise ทุกตัว resolve ด้วยค่า dismiss ของ kind นั้น
- เปลี่ยน route แบบ Next app router

```tsx
'use client'
import { usePathname } from 'next/navigation'
import { DialogHost } from 'react-confirm-alert'

export function Dialogs() {
  return <DialogHost dismissKey={usePathname()} />
}
```

router อื่นใช้ `closeAll()` ใน listener ของ router นั้น

### 2.9 สภาพแวดล้อม

- **SSR** import แล้วไม่แตะ `window` หรือ `document` ที่ระดับ module `DialogHost` render `null` บน server เพราะ store ว่าง จึงไม่มี hydration mismatch ถ้าเรียก `confirm()` บน server Promise จะ reject ด้วย `Error('react-confirm-alert: dialogs need a browser')` ส่วน `<Dialog>` และ `<ConfirmDialog>` render `null` จนกว่าจะ hydrate เสร็จ (ใช้ `useSyncExternalStore` ที่ `getServerSnapshot` คืน `false`) เพราะ modal ใช้ไม่ได้อยู่แล้วถ้าไม่มี JS และวิธีนี้ทำให้ `classNames` จาก `configureDialogs` ที่เรียกฝั่ง client เท่านั้นไม่ทำให้ hydration mismatch
- **Next app router** ไฟล์ entry ขึ้นต้นด้วย `'use client'` (ต้องใส่ผ่าน `output.banner` เพราะ Rollup ตัด directive ระดับ module ออกตอนรวมไฟล์) ผู้ใช้ import `DialogHost` ใน `layout.tsx` ที่เป็น server component ได้
- **React 18 และ 19** peer `react` คง `>=18.0.0` แบบ v3 และ `react-dom` แก้จาก `>=10.0.0` เป็น `>=18.0.0` ไม่ใช้ `^18 || ^19` เพราะเมื่อ React 20 ออก npm 7 ขึ้นไปจะ install ไม่ผ่าน (ERESOLVE) ทั้งที่ code อาจทำงานได้ CI ทดสอบ 18 และ 19 ใช้แค่ `useSyncExternalStore`, `useId`, `useEffect`, `createRoot` ไม่ใช้ `propTypes`, `defaultProps` บน function component, `forwardRef`, `findDOMNode` หรือ `element.ref` ซึ่ง 19 ลบหรือ deprecate แล้ว effect ที่เรียก `showModal()` ต้องเช็ก `dialog.open` ก่อนเรียก และ cleanup ต้องเรียก `close()` เพื่อให้ StrictMode ที่รัน effect สองรอบไม่ throw `InvalidStateError`
- **ESM และ CJS** ดูหัวข้อ 3.6
- **Vite** ไม่มี runtime dependency (ต้นเหตุ #85 คือ `prop-types` ที่ไม่ได้ประกาศ) และ Vite เลือก ESM build ผ่าน field `module` จึงไม่ต้องตั้งค่า
- **Test และ mock (#48)** ฟังก์ชันทุกตัวคืน Promise จึง mock ได้ตรง ๆ

```ts
vi.mock('react-confirm-alert', () => ({ confirm: vi.fn().mockResolvedValue(true) }))
// Jest: jest.mock('react-confirm-alert', () => ({ confirm: jest.fn().mockResolvedValue(true) }))
```

ถ้าอยากทดสอบผ่าน dialog จริงใน jsdom lib ต้องทำงานได้เมื่อ `HTMLDialogElement.prototype.showModal` ไม่มี โดย fallback เป็นตั้ง attribute `open` และย้าย focus เอง (เท่าที่ทราบ jsdom ยังไม่ implement `showModal` ต้องยืนยันกับ jsdom เวอร์ชันล่าสุดใน P0) ผู้ใช้จึงเขียน `await user.click(screen.getByRole('button', { name: 'ตกลง' }))` ได้

### 2.10 Styling, Tailwind และ unstyled

มีสี่ทางให้แต่ง เรียงจากแตะน้อยไปมาก ทุกทางใช้ markup ชุดเดียวกัน

1. import CSS เริ่มต้น แล้วเปลี่ยน CSS variable
2. import CSS เริ่มต้น แล้วเติม class ของ Tailwind ผ่าน `classNames` ทับบางส่วน
3. `unstyled: true` ไม่ import CSS แล้วใช้ Tailwind ล้วน
4. `openDialog({ render })` เขียนเนื้อหาเอง ส่วน `dialog` และ `panel` ยังรับ `classNames` และ data attribute เหมือนข้ออื่น

#### Slot, type และค่าเริ่มต้นระดับแอป

```ts
export type DialogSlot =
  | 'dialog'   // <dialog> เต็มจอ โปร่งใส มี ::backdrop
  | 'panel'    // กล่องที่มองเห็น คลิกนอกกล่องนี้คือคลิกนอก
  | 'body'     // wrapper ของเนื้อหา alert, confirm และ prompt (custom ไม่มี)
  | 'title'
  | 'message'
  | 'actions'  // กลุ่มปุ่ม
  | 'button'
  | 'field'    // wrapper ของ prompt
  | 'label'
  | 'input'
  | 'error'    // ข้อความจาก validate

export type DialogClassNames = Partial<Record<DialogSlot, string>>

export interface DialogDefaults {
  unstyled?: boolean
  classNames?: DialogClassNames
  closeOnEscape?: boolean
  closeOnClickOutside?: boolean
  strategy?: Strategy
  modal?: boolean
  lockScroll?: boolean        // default true ใส่ class react-confirm-alert-body-element และ overflow: hidden ที่ <body> แบบ v3
  confirmAlert?: Pick<DialogDefaults, 'modal' | 'strategy' | 'unstyled' | 'classNames'>   // ค่าเริ่มต้นแยกของ API v3
  labels?: { ok?: ReactNode; confirm?: ReactNode; cancel?: ReactNode; submit?: ReactNode }
}

// เรียกครั้งเดียวที่ฝั่ง client ก่อนเปิด dialog แรก เรียกซ้ำแล้วแทนที่ค่าเดิมทั้งชุด
export function configureDialogs(defaults: DialogDefaults): void
```

กฎการรวม class ต่อ slot คือ `[class ของ v3 ถ้าไม่ unstyled] + defaults.classNames[slot] + options.classNames[slot] + button.className (เฉพาะปุ่ม)` ต่อกันด้วยช่องว่าง lib ไม่แก้ class ที่ชนกันเอง (ไม่มี `tailwind-merge`) ถ้าต้องการให้ class ต่อครั้งชนะ class ระดับแอป ให้ใช้ modifier `!` ของ Tailwind หรือย้าย class นั้นออกจาก defaults

`unstyled: true` แปลว่า lib ไม่ใส่ class `react-confirm-alert-*` และไม่ใส่ inline style ใด ๆ ให้แค่ `classNames`, data attribute และ ARIA ส่วนพฤติกรรม (focus, Esc, คลิกนอก, scroll lock, รอ animation ปิด) เหมือนเดิมทุกอย่าง CSS เริ่มต้นจับ element ด้วย class ของ v3 เท่านั้น ถ้ายัง import ไฟล์ CSS ค้างไว้ dialog ที่ unstyled จึงไม่โดน style

## 3. การตัดสินใจหลัก

### 3.1 ใช้ `<dialog>` แบบ native และ top layer

**ใช้ เมื่อ `modal: true`** (ค่าเริ่มต้นของ API ใหม่) เพราะแก้ปัญหาที่ v3 เขียนเองแล้วพังได้ทีเดียวสามข้อ top layer ไม่ต้องแข่ง z-index (#31) `showModal()` ทำให้พื้นหลัง inert และย้าย focus เข้า dialog (#29) และ `::backdrop` แทน SVG blur ที่ผูกกับ `body.children[0]` (#77)

**frame มีสองแบบตามค่า `modal` และ component เดียวกัน (`DialogFrame`) เลือก** `modal: true` และ browser มี `showModal` ได้ `<dialog>` ที่เปิดด้วย `showModal()` ใน `useLayoutEffect` (ก่อน paint จึงไม่กระพริบ) นอกนั้นได้ `div role="dialog"` แบบ v3 ทุกอย่าง (`position: fixed`, `z-index: 99` จาก CSS) และย้าย focus เข้าเองโดยไม่กัก focus ไว้ เหตุผลที่ `confirmAlert` ยังใช้ `div` เป็นค่าเริ่มต้นคือ top layer กับ inert เปลี่ยนสิ่งที่ผู้ใช้เห็นโดยไม่ได้เลือก toast, chat widget หรือ header ที่เคยตั้ง z-index สูงกว่า 99 ไว้ให้อยู่เหนือ dialog จะไปอยู่ใต้ dialog และกดไม่ได้ทันที (ตาราง 4.2) ส่วนตัว `<dialog>` เองไม่มี CSS ที่ตั้ง `display` ตอนไม่ได้เปิด เพราะ `display` ที่ผู้เขียนตั้งชนะ `dialog:not([open]) { display: none }` ของ browser

สิ่งที่ต้องเขียนเองเพราะ browser ไม่ทำให้

- **โครงของ DOM** frame (`<dialog>` หรือ `div`) เต็มจอและโปร่งใสเหมือน overlay ของ v3 ส่วนกล่องที่มองเห็นคือ slot `panel` ที่อยู่ข้างใน ทั้งโหมด CSS เริ่มต้นและ unstyled ใช้โครงนี้ กฎจึงเป็นข้อเดียวว่า "`panel` คือกล่อง" ซึ่งทำให้ class ของ v3 (`.react-confirm-alert-overlay` บน `<dialog>`, `.react-confirm-alert` บน `panel`) ยังจับ element ที่หน้าที่เดิม
- **คลิกนอกกล่อง** ปิดเมื่อ target ของทั้ง `pointerdown` และ `click` คือตัว `<dialog>` เอง เพราะ `<dialog>` เต็มจอ พื้นที่รอบ `panel` (รวม padding ของ `<dialog>`) จึงเป็นพื้นที่ "นอก" ส่วน element ลูกทุกตัวนับเป็น "ใน" รวม popover ของ lib อื่นที่ portal เข้ามาใน `<dialog>` (ต้องอยู่ตรงนั้นเพราะส่วนอื่นของหน้า inert) การจำ target ของ `pointerdown` คือสิ่งที่แก้ #92 ไม่ใช้ `!panel.contains(target)` เพราะคลิกใน popover ที่อยู่นอก `panel` จะปิด dialog
- **Esc เมื่อ `closeOnEscape: false`** เรียก `preventDefault()` ใน event `cancel` ความเสี่ยงคือ Chrome อาจยอมให้ Esc ซ้ำปิด dialog แม้ถูก `preventDefault` (พฤติกรรมของ CloseWatcher) นี่เป็นสิ่งที่จำได้ ยังไม่ได้วัด P2 ต้องมี test ใน Chromium ถ้าเกิดจริงให้ฟัง `close` แล้ว `showModal()` ใหม่
- **ไม่ใช้ attribute `closedby`** เพราะ Safari ยังไม่รองรับ
- **jsdom** fallback ตามข้อ 2.9

### 3.2 root แยกหรือ portal ใน provider

**ใช้ทั้งสองแบบ แต่เป็น render path เดียว** component ที่ render entry มีตัวเดียว (`DialogStack`) ถ้ามี `<DialogHost>` ถูก mount `DialogStack` อยู่ใน tree ของแอป ถ้าไม่มี lib สร้าง root แยกที่ render `DialogStack` ตัวเดียวกัน ไม่มีการใช้ `createPortal` เพราะ top layer ทำให้ไม่ต้องย้าย DOM

เหตุผลที่ไม่เลือกแบบเดียว ถ้าบังคับ host ผู้ใช้ v3 ทุกคนต้องแก้ code ตอนอัปเกรด ถ้าใช้ root แยกอย่างเดียว ปัญหา context (#23 #28 #35 #94) แก้ไม่ได้

### 3.3 Motion ที่เคารพ `prefers-reduced-motion`

- CSS เริ่มต้นมี animation ขาเปิดแบบ v3 (fade-in) บน `.react-confirm-alert-overlay` ระยะเวลาและ delay เป็น `--rca-duration` และ `--rca-delay` (ค่าตามคำถามข้อ 2) และ**ไม่มี animation ขาปิด** เหมือน v3 การปิดในค่าเริ่มต้นจึงเกิดทันที ไม่เปลี่ยนจังหวะที่ test ของผู้ใช้ v3 พึ่งอยู่ ผู้ใช้ที่อยากได้ขาปิดเพิ่มเองด้วย CSS 3 บรรทัดหรือ class ของ Tailwind (หน้า motion ในเว็บเอกสาร)
- ปิดด้วยการตั้ง `phase: 'closing'` ซึ่ง render เป็น `data-state='closing'` แล้วรอ animation ของตัว `<dialog>` และ `::backdrop` จบก่อนเรียก `dialog.close()` และลบ entry ใช้ `dialog.getAnimations({ subtree: true })` แล้วกรองเหลือเฉพาะตัวที่ `effect.target` เป็น `dialog` หรือ `panel` (ครอบ `::backdrop` ด้วย ซึ่งเรียกแบบไม่มี `subtree` จะไม่ได้) ห้ามรอ animation ของลูกตัวอื่น animation ที่นับรวม CSS transition ด้วย class ของ Tailwind เช่น `data-[state=closing]:opacity-0` จึงถูกรอเหมือน keyframe เพราะ animation แบบ infinite เช่น spinner ของปุ่ม busy ไม่มีวันจบ ไม่ใช้ `setTimeout` เดาเวลา จึงไม่ค้างถ้าผู้ใช้ override CSS ถ้ากรองแล้วไม่เหลือ animation เลย ให้ปิดแบบ synchronous ในจังหวะเดียวกัน ไม่ผ่าน `Promise.all([])` ที่เลื่อนไป microtask ถัดไป จังหวะจึงตรงกับ v3
- `@media (prefers-reduced-motion: reduce)` ตั้ง `animation: none` เมื่อไม่มี animation `getAnimations()` คืน array ว่าง dialog ปิดทันที ตรรกะ JS ไม่ต้องเช็ก media query เอง
- ไม่ใช้ `@starting-style` กับ `transition-behavior: allow-discrete` เป็นทางหลัก เพราะ Firefox เพิ่งรองรับ (129) และ exit transition ของ top layer ยังต่างกันในแต่ละ browser keyframe ทำงานเหมือนกันทุกที่

### 3.4 Focus และ a11y

- `role="alertdialog"` สำหรับ alert และ confirm, `role="dialog"` สำหรับ prompt และ custom
- `aria-labelledby` และ `aria-describedby` ผูกกับ id จาก `useId()` ส่งให้ custom ผ่าน `titleId` และ `descriptionId`
- focus เริ่มต้น confirm ปกติไปที่ปุ่มยืนยัน, `tone: 'danger'` ไปที่ปุ่มยกเลิก, prompt ไปที่ช่องกรอก, custom ไปที่ element ที่มี `autoFocus` ตัวแรก ถ้าไม่มีให้ browser เลือก ส่วน `confirmAlert` ไปที่ `panel` เสมอ (B14)
- คืน focus ไปที่ element ที่ focus ก่อนเปิด หลังปิด ถ้า element นั้นยังอยู่ใน DOM (ทำเองแม้ spec ใหม่จะทำให้ เพราะ fallback ใน jsdom ไม่ทำ)
- prompt ใช้ `<form method="dialog">` กด Enter แล้ว submit โดย handler ต้อง `preventDefault()` เสมอ ไม่อย่างนั้น browser ปิด dialog เองทันที ข้าม `validate` และ animation ปิด, error จาก `validate` ผูกด้วย `aria-invalid` และ `aria-describedby`
- scroll lock ใช้ class `react-confirm-alert-body-element` บน `body` แบบ v3 (ชื่อเดิมเพื่อให้ CSS ของผู้ใช้ยังใช้ได้) และใส่ inline `overflow: hidden` ที่ `body` ตัวเดียวกันเฉพาะตอน `unstyled` (เพราะไม่มี CSS ของ lib ให้ class ทำงาน) จึงเป็น element เดิมของ v3 ไม่มี layout shift แบบใหม่ ตั้งเมื่อมี entry ที่ `open` อย่างน้อยหนึ่งตัว ลบเมื่อไม่มี คำนวณจาก store ไม่ใช่ add/remove ตามแต่ละ dialog จึงไม่หลุดเมื่อซ้อนกัน

### 3.5 Zero runtime dependency

`dependencies` ว่าง มีแค่ `peerDependencies` ของ `react` และ `react-dom` ลบ `prop-types` (ต้นเหตุ #85, และ React 19 ไม่อ่าน `propTypes` แล้ว) TypeScript ทำหน้าที่ตรวจ props แทน devDependency ที่เพิ่มจะระบุในแต่ละ phase

### 3.6 Build ด้วย Vite library mode โดยไม่ย้าย path เดิม

3.1.0 ไม่ใส่ `exports` map และไม่ใส่ `"type": "module"` เพราะทั้งสองอย่างเปลี่ยนวิธี resolve ของผู้ใช้ทุกคน `exports` บล็อก deep import ที่ไม่ได้ประกาศ และ `"type": "module"` เปลี่ยนความหมายของไฟล์ `.js` ทุกไฟล์ ESM มาทาง field `module` แบบที่ bundler ใช้มาตั้งแต่ก่อนมี `exports` ซึ่งได้ tree-shaking ครบโดยไม่แตะ Node

- `vite build` (library mode) ออกสองไฟล์ externalize `react`, `react-dom`, `react-dom/client`, `react/jsx-runtime`
  - CJS ที่ `lib/index.js` path เดิมของ v3 ทุกตัวอักษร คนที่ `require('react-confirm-alert/lib/index.js')` ยังได้ไฟล์
  - ESM ที่ `dist/index.esm.js` นามสกุล `.js` ไม่ใช่ `.mjs` เพราะ webpack 4 อ่านไฟล์ `.mjs` แบบ ESM เข้มงวดและ import ชื่อจาก `react` ที่เป็น CJS ไม่ได้ (ต้องยืนยันด้วย `fixtures/webpack4`)
- lib ไม่ import CSS จาก JS ไฟล์ CSS คือ `src/react-confirm-alert.css` ที่เขียนมือและ ship ตรงตัวแบบ v3 ไม่ผ่าน Vite จึงไม่มีเรื่องชื่อไฟล์ CSS ของ library mode
- type ออกด้วย `tsc --emitDeclarationOnly` แล้วรวมเป็นไฟล์เดียวด้วย `rollup-plugin-dts` (devDependency) เขียนทับ `index.d.ts` ที่ root path เดิม (`typings` ไม่เปลี่ยน) ไวยากรณ์ใน `.d.ts` ต้องอ่านได้ด้วย TypeScript 4.7 (`fixtures/ts-min`) เพื่อไม่ให้ผู้ใช้ TS เก่าที่ไม่ได้ตั้ง `skipLibCheck` compile พัง
- `'use client'` ใส่ผ่าน `build.rollupOptions.output.banner` ทั้งสองไฟล์ เพราะ Rollup ตัด directive ระดับ module ออกตอนรวมไฟล์
- `package.json` ของ 3.1.0

```json
{
  "main": "lib/index.js",
  "module": "dist/index.esm.js",
  "typings": "./index.d.ts",
  "sideEffects": ["**/*.css"],
  "files": ["lib", "dist", "src/react-confirm-alert.css", "index.d.ts"],
  "peerDependencies": { "react": ">=18.0.0", "react-dom": ">=18.0.0" }
}
```

- 4.0.0 (P9) ค่อยเพิ่ม `exports` map ที่ประกาศทุก path ที่ v3 ship (`./lib/index.js`, `./lib/index`, `./lib`, `./src/react-confirm-alert.css`, `./index.d.ts`, `./package.json`) บวก `./style.css` และ ESM แบบ `.mjs` สำหรับ Node พร้อม `.d.mts` เพราะการเปลี่ยน `import pkg from 'react-confirm-alert'` ใน Node ESM จาก object ของ CJS เป็น class จริงคือ breaking change
- `demo/bundle.js` ที่ commit ไว้ และ `webpack.config*.js`, `.babelrc`, `configs/` ลบทิ้ง demo ใหม่ build ใน CI

### 3.7 TypeScript strict แบบ discriminated union

- `tsconfig` เปิด `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`
- options แยกด้วย `kind` (ข้อ 2.2) `DialogStack` เลือก renderer ผ่าน table `const renderers = { alert, confirm, prompt, custom } satisfies Record<Kind, ...>` ไม่ใช่ if/else ต่อกัน เพิ่ม kind ใหม่แล้วลืม renderer จะ compile ไม่ผ่าน
- `DialogId` เป็น branded string สร้างได้จาก store เท่านั้น
- type ของ public API ทดสอบด้วยไฟล์ `*.test-d.ts` ผ่าน `vitest typecheck` เช่น `expectTypeOf(confirm('x')).resolves.toEqualTypeOf<boolean>()` และ `// @ts-expect-error` สำหรับ `kind: 'prompt'` ที่ส่ง `confirmLabel`

### 3.8 CSS เริ่มต้นไม่ห่อ cascade layer เอง

ไฟล์ CSS คง selector และ specificity แบบ v3 ทุก rule เปลี่ยนแค่ค่าคงที่เป็น `var(--rca-*, ค่าเดิม)` จึงไม่มี rule ไหนของผู้ใช้ที่เคยแพ้แล้วกลับมาชนะ หรือเคยชนะแล้วกลับไปแพ้ ถ้า lib ห่อทั้งไฟล์ด้วย `@layer` CSS ที่ผู้ใช้เขียนนอก layer จะชนะทุก rule ทันที rule ที่เคยแพ้ specificity มาตลอดจะเริ่มมีผล ซึ่งเปลี่ยนหน้าตาโดยผู้ใช้ไม่ได้แก้อะไร

ผู้ใช้ Tailwind v4 เลือก layer เองตอน import ด้วย `@import 'react-confirm-alert/src/react-confirm-alert.css' layer(components);` แล้ว utility ชนะเสมอ ข้อนี้จริงเฉพาะ declaration ปกติ เพราะ `!important` ใน layer ชนะ `!important` นอก layer จึงตั้งกฎว่าไฟล์ CSS ห้ามมี `!important` และ CI เช็กด้วย `! grep -q '!important' src/react-confirm-alert.css` ลำดับ layer ขึ้นกับว่า CSS ไหนปรากฏก่อน เอกสารจึงแนะนำให้ผู้ใช้ Tailwind import ผ่าน `@import` ใน CSS หลักเท่านั้น ไม่ import จาก JS

### 3.9 เว็บเอกสารเป็น npm workspace ไม่ใช่ monorepo เต็มรูป

- **ไม่ย้าย lib ไป `packages/`** lib อยู่ที่ root ต่อไป เพราะ `git blame`, ลิงก์ใน issue เก่า, path ใน `npm pack` และ README ที่คนลิงก์ไว้ยังชี้ที่เดิม monorepo เต็มรูปเพิ่มความซับซ้อนของ release โดยผู้ใช้ไม่ได้อะไร
- **เว็บอยู่ที่ `website/`** เป็น workspace ของ npm (`"workspaces": ["website"]` ใน root `package.json`) ไม่ใช้ชื่อ `docs/` เพราะ `docs/plans/` ใช้เก็บ plan อยู่แล้ว และ `files: ["dist"]` ของ lib กันไม่ให้ `website/` ติดไปกับ package
- **เว็บใช้ lib ผ่าน workspace link** `website/package.json` ระบุ `"react-confirm-alert": "*"` npm link ไปที่ root จึงใช้ `main`, `module` และไฟล์ที่ build แล้วจริง ต้อง build lib ก่อน build เว็บ เว็บจึงเป็น consumer อีกตัวที่จับ packaging ที่พังได้ `react` และ `react-dom` ต้องเป็นเวอร์ชันเดียวกับ devDependency ของ root ไม่อย่างนั้นจะมี React สองชุด
- **Fumadocs บน Next.js static export** `output: 'export'`, `basePath: '/react-confirm-alert'`, `trailingSlash: true`, `images: { unoptimized: true }` ค้นหาใช้ Orama แบบ static (`staticGET` ใน `app/api/search/route.ts` คู่กับ client แบบ static ของ Fumadocs UI) ซึ่งสร้าง index ตอน build ไม่ต้องมี server ตัวเว็บใช้ Tailwind v4 อยู่แล้ว (Fumadocs UI ใช้) หน้า recipe ของ Tailwind จึงรันบนเว็บจริงได้
- **ตัวอย่างใน MDX มาจากไฟล์ที่รันจริง** แต่ละ scenario เป็นไฟล์ `.tsx` ไฟล์เดียว หน้า MDX render component นั้นสด และแสดง source ด้วย `<include>` ของ fumadocs-mdx code ที่โชว์จึงเป็น code เดียวกับที่รัน

### 4.2 Breaking change ทุกข้อที่หาเจอ

### 4.3 ออกเป็น 3.x minor แทน v4 ได้ไหม

**ได้ และแนะนำ (คำถามข้อ 0)** เหตุผลมีสี่ข้อ

1. **ไม่มีข้อไหนในตาราง 4.2 ที่ทำให้ code ที่ทำงานถูกใน v3 พังโดยผู้ใช้ไม่ได้เลือก** ข้อที่ผู้ใช้เจอใน 3.1.0 มีแค่ bug fix (B12 B13 B14 B15 B18 B21) การเปลี่ยนที่มองไม่เห็นในการใช้ปกติ (B16 B17) และ snapshot ของ DOM (B20) semver ยอมให้ bug fix อยู่ใน minor และ snapshot test ของ DOM ภายใน lib ไม่ใช่สัญญาที่ README เคยให้ไว้
2. **API ใหม่ทั้งหมดเป็นของเพิ่ม** (`confirm`, `alert`, `prompt`, `openDialog`, `DialogHost`, `Dialog`, `ConfirmDialog`, `configureDialogs`, `classNames`, `unstyled`) ไม่มีชื่อเดิมถูกใช้ความหมายใหม่
3. **fix ไปถึงผู้ใช้จริง** `npm install` เขียน `^3.0.6` ให้ ผู้ใช้ส่วนใหญ่จะได้ 3.1.0 ตอน `npm install` หรือ `npm update` ครั้งถัดไป ถ้าออกเป็น 4.0.0 ต้องมีคนตั้งใจอัปเกรด ข้อนี้ประเมินจากพฤติกรรมของ npm ไม่ได้วัดสัดส่วนจริง
4. **4.0.0 ทีหลังจะเล็กและอธิบายง่าย** เหลือแค่เปลี่ยนค่าเริ่มต้นของ `confirmAlert` เป็นแบบ API ใหม่และเพิ่ม `exports` map (P9) ผู้ใช้ที่อยากได้พฤติกรรมของ 4.0.0 ก่อนก็ตั้ง `configureDialogs({ confirmAlert: { modal: true, strategy: 'stack' } })` ได้ตั้งแต่ 3.1.0

**ราคาที่ต้องจ่าย** ความผิดพลาดใน 3.1.0 จะไปถึงผู้ใช้ `^3` ทุกคนพร้อมกัน ไม่มีใครเลือกได้ว่าจะยังไม่รับ ทางรับมือคือ contract test ในข้อ 4.1 ที่รันกับ `src/index.js` ของ v3 ก่อน (P0) แล้วรันกับของใหม่ทุก PR, fixture 8 แบบ (P1), beta บน `next` อย่างน้อย 2 สัปดาห์ (P7) และถ้ายังพลาด ให้ออก 3.1.1 แก้ทันที แล้ว `npm deprecate` 3.1.0 พร้อมข้อความชี้ไปเวอร์ชันที่แก้

**เมื่อไรไม่ควรออกเป็น minor** ถ้าเจ้าของ lib อยากให้ `confirmAlert` เป็น modal (top layer) ตั้งแต่วันแรก B1 จะกลายเป็น breaking change จริง ต้องออกเป็น 4.0.0

### 4.4 ทางย้ายที่แนะนำ

1. อัปเกรดเป็น 3.1.0 โดยไม่แก้อะไร `confirmAlert` ทำงานเหมือนเดิม
2. วาง `<DialogHost />` ใต้ provider ของแอป (Redux, Intl, theme) dialog ทุกตัวจะได้ context ทันที
3. ตั้ง `configureDialogs({ confirmAlert: { modal: true, strategy: 'stack' } })` เพื่อรับพฤติกรรมของ 4.0.0 ล่วงหน้า แล้วตรวจ toast และ widget ที่ควรอยู่เหนือ dialog
4. ย้ายจุดเรียกทีละจุดจาก `confirmAlert({ buttons: [...] })` เป็น `if (await confirm(...))`
5. dialog ที่ต้องอ่าน state ของ component ย้ายไปเป็น `<Dialog open>`

หน้า migrate บนเว็บเอกสาร (P6) มีตัวอย่างก่อนและหลังของแต่ละข้อ และตาราง 4.2 ทั้งตาราง

### P7 Publish ขึ้น npm

เป้า ทุก release ออกจาก GitHub Actions เท่านั้น ด้วย npm trusted publishing (OIDC) ที่แนบ provenance ไม่มี npm token เก็บไว้ที่ไหน beta ออกบน dist-tag `next` ก่อน แล้วค่อยออกตัวจริงบน `latest`

- ไฟล์

    - `"check:package": "publint --strict && attw --pack . && size-limit"`
    - `"version-packages": "changeset version && npm install --package-lock-only"`
    - `"release": "npm run build && npm run check:package && changeset publish"`
  - `.changeset/config.json` ตั้ง `"changelog": ["@changesets/changelog-github", { "repo": "GA-MO/react-confirm-alert" }]` และ `"baseBranch": "master"` changelog-github ใส่ "Thanks @user!" และลิงก์ PR ให้ผู้ส่ง PR ที่มี changeset เอง
  - `.changeset/*.md` หนึ่งไฟล์ต่อหนึ่งการเปลี่ยนที่ผู้ใช้เห็น เขียนตั้งแต่ P1 ถึง P6 ทีละ PR สำหรับแนวคิดที่ adopt จาก PR ของคนอื่น (ภาคผนวก A) ใส่บรรทัด `author: @<ผู้ส่ง>` และ `pr: #<เลข>` ใน changeset เพื่อให้ changelog-github ให้เครดิตคนที่คิด ไม่ใช่คนที่ทำ (รูปแบบนี้ต้องยืนยันกับเอกสารของ changelog-github ตอนตั้งค่า) และใส่ `Co-authored-by` ใน commit เมื่อใช้ code ของเขา
  - `.github/workflows/ci.yml` รัน `tsc`, `vitest` (สาม browser), `vitest typecheck`, fixture ทั้งหมด, `npm run check:package`, `! grep -q '!important' src/react-confirm-alert.css` และ `npm publish --dry-run` ทุก PR

```yaml
      contents: write          # changeset publish สร้าง git tag

      - run: git push --follow-tags
```

job `publish` ถูกเรียกทุก push ที่ไม่มี changeset ค้าง รวม push ที่ไม่มีอะไรจะ publish ด้วย ในกรณีนั้น `changeset publish` ไม่ทำอะไร แต่ยังต้องรออนุมัติ environment ถ้ารบกวน ให้เพิ่ม step แรกใน job `version` ที่เทียบ `version` ใน `package.json` กับ `npm view react-confirm-alert versions` แล้วส่ง output `shouldPublish` ไปใช้แทน

- เหตุผลของค่าใน workflow ทุกข้อมาจากเอกสาร trusted publishing ของ npm (docs.npmjs.com/trusted-publishers) ที่อ่านวันที่ 2026-10-23 คือ ต้องใช้ npm 11.5.1 ขึ้นไปและ Node 22.14.0 ขึ้นไป, ต้องมี `id-token: write`, ใช้ได้เฉพาะ GitHub-hosted runner และ provenance แนบให้เองเมื่อ repo กับ package เป็น public ส่วนข้อห้ามตั้ง `registry-url` และ `NODE_AUTH_TOKEN` (ค่าว่างทำให้ OIDC ไม่ทำงาน) มาจากรายงานของผู้ใช้ ยังไม่ได้ยืนยัน beta ตัวแรกเป็นตัวยืนยัน การ publish จึงไม่ผ่าน `changesets/action` เลย เพราะ action รุ่น v1 เก่าบางรุ่นเขียน `_authToken=${NPM_TOKEN}` ลง `~/.npmrc` เสมอ ซึ่งเมื่อไม่มี secret อาจขวาง OIDC (ยังไม่ได้ยืนยัน)
- ลำดับการออก

  3. ช่วง beta (คำถามข้อ 5) แก้ bug ด้วย PR ที่มี changeset ทุก merge ของ PR version ออก `-next.N` ตัวถัดไป
  4. agent เปิด PR ที่รัน `npx changeset pre exit` แล้วเจ้าของ merge, merge PR version ที่ได้ `3.1.0` และอนุมัติ ได้ `3.1.0` บน `latest`

## 6. ตัวเลขที่จะวัดและใส่ใน README

วัดด้วย size-limit ทั้งหมด (`@size-limit/preset-small-lib` ซึ่ง bundle ด้วย esbuild แล้วบีบ) ไม่เขียน script วัดเอง config อยู่ใน `.size-limit.json` และ CI ใช้ไฟล์เดียวกันเป็นงบ

```json
[
  { "name": "confirmAlert (v3 API)", "path": "dist/index.esm.js", "import": "{ confirmAlert }", "ignore": ["react", "react-dom"], "gzip": true, "limit": "2.5 kB" },
  { "name": "confirm()", "path": "dist/index.esm.js", "import": "{ confirm }", "ignore": ["react", "react-dom"], "gzip": true, "limit": "3 kB" },
  { "name": "DialogHost + useDialog", "path": "dist/index.esm.js", "import": "{ DialogHost, useDialog }", "ignore": ["react", "react-dom"], "gzip": true, "limit": "3 kB" },
  { "name": "ทั้ง package (CJS)", "path": "lib/index.js", "ignore": ["react", "react-dom"], "gzip": true, "limit": "4 kB" },
  { "name": "CSS", "path": "src/react-confirm-alert.css", "gzip": true, "limit": "1 kB" }
]
```

- ต้องตั้ง `"gzip": true` เพราะ size-limit รุ่นใหม่วัดแบบ brotli เป็นค่าเริ่มต้น ตัวเลขใน README บอกว่าเป็น gzip
- baseline v3.0.6 วัดใน P0 ด้วย config ชั่วคราวที่ชี้ `fixtures/v3-baseline/node_modules/react-confirm-alert/lib/index.js` (ติดตั้งจาก `npm pack react-confirm-alert@3.0.6`) v3 ไม่ tree-shake และพา `prop-types` มาด้วย จึงวัดทั้งไฟล์รวม `prop-types`
- งบในตารางเป็นเป้า ยังไม่ได้วัด P0 ปรับตาม baseline ได้
- README แสดงตาราง `npx size-limit --json` พร้อมเวอร์ชันของ size-limit และวันที่วัด และบอกคำสั่งให้ผู้อ่านรันซ้ำได้ ไม่ใช้ตัวเลขจาก bundlephobia เพราะวัดด้วยค่าตั้งที่เราไม่ได้คุม
- หน้าแรกของเว็บเอกสารอ่านตัวเลขจากไฟล์ JSON ที่ `size-limit --json` เขียนตอน build ไม่ได้พิมพ์ตัวเลขด้วยมือ
